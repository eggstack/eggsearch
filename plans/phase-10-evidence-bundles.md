# Phase 10 Plan: Evidence Bundles for Multi-Agent Handoff

## Objective

Introduce a deterministic, non-summarizing evidence bundle object that codegg agents can pass across manager, coder, reviewer, security, and research loops without repeating search and fetch work. The bundle should preserve source IDs, provenance, trust markers, selected fetch spans, quality signals, unresolved gaps, and provider diagnostics.

This phase should not add model summarization or autonomous crawling. The bundle is a structured evidence container. It should make prior search/fetch work reusable, inspectable, bounded, and safe for agent handoff.

## Current baseline

The repo already has the core pieces required for evidence bundles:

- `web_search`, `repo_search`, `security_search`, and `research_search` return source cards, groups, warnings, trust markers, provider failures, and suggested fetches.
- `web_fetch`, `repo_fetch`, and `batch_fetch` return bounded content with trust labels and structured document/span metadata.
- `repo_fetch` supports line ranges, symbol/match text, and selected span metadata.
- Local workspace results are labeled separately from external untrusted content.
- Provider routing and failure telemetry are visible.

The missing layer is a stable object that packages selected evidence and metadata for reuse by other agents without losing source identity or trust context.

## Non-goals

Do not summarize evidence in this phase. Do not ask a model to judge source relevance. Do not fetch additional URLs automatically beyond explicit selected fetch requests. Do not persist bundles server-side unless explicitly added behind a future storage design. Do not invent source IDs that cannot be traced back to response inputs.

## User-facing behavior

Agents should be able to do flows like:

1. Run `repo_search` for a symbol or error.
2. Fetch selected source spans via `repo_fetch` or `batch_fetch`.
3. Build an evidence bundle from search results and fetch responses.
4. Pass the bundle to another agent.
5. The receiving agent can inspect source IDs, source kinds, trust markers, warnings, selected spans, gaps, and provider diagnostics.

The bundle is not a conclusion. It is a container for evidence and metadata.

## Proposed tool surface

Prefer adding a single tool only if it makes the workflow simpler. Candidate:

- `evidence_bundle` or `build_evidence_bundle`.

Alternative: add bundle-building helpers inside `batch_fetch` responses. The cleaner approach is a dedicated tool because it can combine search and fetch artifacts without changing existing tools heavily.

### Proposed request

```rust
pub struct EvidenceBundleRequest {
    pub goal: Option<String>,
    pub search_responses: Vec<EvidenceSearchInput>,
    pub fetch_responses: Vec<EvidenceFetchInput>,
    pub include_unfetched_sources: Option<bool>,
    pub max_sources: Option<usize>,
    pub max_fetched_items: Option<usize>,
    pub max_total_chars: Option<usize>,
}
```

For MCP, raw JSON response objects may be accepted if the current MCP framework can handle structured values. If passing full prior responses is too large, support compact references/selected source objects generated by existing tools.

### Proposed response

```rust
pub struct EvidenceBundle {
    pub bundle_id: String,
    pub goal: Option<String>,
    pub created_at: String,
    pub sources: Vec<EvidenceBundleSource>,
    pub fetched_items: Vec<EvidenceBundleFetchedItem>,
    pub source_links: Vec<EvidenceBundleLink>,
    pub trust_summary: EvidenceTrustSummary,
    pub provider_summary: EvidenceProviderSummary,
    pub gaps: Vec<EvidenceGap>,
    pub warnings: Vec<SearchWarning>,
    pub limits: EvidenceBundleLimits,
}
```

`bundle_id` should be deterministic from canonicalized content where possible. Do not require server persistence.

### Gaps

Gaps should be deterministic, not model-generated. Examples:

- `no_primary_source_found`.
- `provider_degraded`.
- `native_repo_filter_not_enforced`.
- `security_applicability_unknown`.
- `fetch_failed`.
- `source_unfetched`.
- `all_results_external_untrusted`.
- `local_checkout_dirty`.

## Workstream 1: Canonical IDs

### Requirements

Generate stable IDs for sources and fetches.

Suggested approach:

- `source_id = src_<short_hash(provider_id + url + title + source_kind)>`.
- `fetch_id = fetch_<short_hash(locator/url + selected range + content hash prefix)>`.
- Preserve original result IDs where available.

IDs must be deterministic across identical inputs. Avoid UUIDs unless deterministic hash inputs are unavailable.

### Tests

- Identical source input yields identical ID.
- URL/title/source-kind changes yield different ID.
- Fetch range changes yield different fetch ID.
- Source/fetch IDs are stable across serialization round trips.

## Workstream 2: Bundle builder

### Implementation

Create `src/core/evidence_bundle.rs` and `src/meta/evidence_bundle.rs` or equivalent.

The builder should:

1. Accept source-card-like inputs from search responses.
2. Accept fetch-response-like inputs from fetch tools.
3. Link fetches back to sources by URL, structured locator, or explicit source ID.
4. Apply bundle caps.
5. Merge warnings and trust markers.
6. Compute deterministic gaps.
7. Produce a bounded response.

Keep the builder pure and testable. MCP tool wrapper should only parse args, validate caps, and serialize output.

### Tests

- Source-only bundle.
- Source + fetched repo span bundle.
- Multiple search responses merged.
- Duplicate source URLs deduplicated deterministically.
- Caps truncate sources/fetches with warnings.
- Trust markers merge correctly.
- Fetch failures become gaps.

## Workstream 3: Tool integration

### MCP tool

Add `build_evidence_bundle` if the MCP schema can reasonably accept structured JSON inputs. If not, expose bundle construction through `batch_fetch` or a new response field on `batch_fetch`.

Tool description should state:

- It does not search.
- It does not fetch.
- It packages already-selected evidence.
- It does not summarize.
- It preserves untrusted/local trust labels.

### Provider status

Add capability:

```json
"evidence_bundle": {
  "enabled": true,
  "summarizes": false,
  "persists": false,
  "max_sources": 50,
  "max_fetched_items": 20
}
```

### Tests

- Tool appears in MCP inventory.
- Provider status advertises evidence-bundle capability.
- Tool rejects empty bundle inputs.
- Tool rejects over-cap inputs or truncates with warnings according to chosen policy.

## Workstream 4: Batch fetch integration

`batch_fetch` is the natural source of multiple fetched items. Add optional bundle-compatible metadata to batch results if useful:

- Preserve item ID.
- Preserve original requested locator/URL.
- Preserve trust per item.
- Preserve source-card link if the item was generated from suggested fetch.

Do not make `batch_fetch` automatically build a bundle unless explicitly requested.

## Workstream 5: Security/research/repo gaps

Implement deterministic gap extraction from existing response fields.

Examples:

### Repo search gaps

- Native repo provider unavailable.
- Symbol hint not enforced.
- Issue/release search unavailable.
- No source files found.
- No tests/examples found.

### Security gaps

- Advisory lookup fallback used.
- Applicability unknown.
- Version missing.
- Package resolution failed.
- No fixed version found.

### Research gaps

- No primary source found.
- No counterpoint found when requested.
- Freshness not enforced.
- Provider degraded.

### Tests

Use fixture responses to assert deterministic gap generation.

## Workstream 6: Documentation and agent workflow

Update README and AGENTS docs with:

- What evidence bundles are and are not.
- Recommended codegg workflow.
- JSON examples for repo-search + repo-fetch + bundle.
- Trust handling.
- Gap semantics.
- Limits and truncation.

## Compatibility requirements

- Do not change existing search/fetch response fields.
- New tool must be optional and capability-advertised.
- Bundle response should be pure JSON with no hidden server state dependency.
- Bundles must preserve trust labels and warnings.
- Bundles must not summarize or reinterpret untrusted content.

## Acceptance criteria

- Evidence bundle core types and builder exist.
- Bundle IDs, source IDs, and fetch IDs are deterministic.
- Sources and fetches are linked where possible.
- Trust markers, warnings, provider diagnostics, and gaps are preserved.
- Bundle building is bounded by configurable caps.
- MCP/tool integration exists or batch-fetch bundle-compatible metadata exists with documented rationale.
- Provider status advertises bundle capability if tool is added.
- Tests cover ID stability, deduplication, caps, trust merging, source/fetch linking, and gap extraction.
- Documentation explains multi-agent handoff workflow and non-summarizing behavior.
