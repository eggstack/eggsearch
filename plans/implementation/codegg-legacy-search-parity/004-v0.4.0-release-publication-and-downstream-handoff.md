## 1. Objective

Publish the already-qualified CodeGG external-search parity surface as immutable
`eggsearch 0.4.0`, prove that the exact published crate/tag/binary release
correspond to one qualified commit, and produce the release evidence needed to
close CodeGG legacy-search-parity M003 and unblock CodeGG's downstream parity
adoption milestone.

This milestone is the operational publication boundary. It is not another
provider-development pass.

The successful sequence is:

```text
release-prep commit (0.4.0)
        |
        v
local release gates on exact candidate
        |
        v
Release binaries: mode=qualify, ref=<exact candidate SHA>
        |
        v
cargo publish --locked
        |
        v
crates.io confirms eggsearch 0.4.0
        |
        v
tag v0.4.0 at exactly QUALIFIED_SHA
        |
        v
tag-triggered Release binaries workflow
        |
        v
review 16-asset draft + attestations
        |
        v
manual GitHub Release publication
        |
        v
external installer/update smoke
        |
        v
closure + registry/downstream handoff reconciliation
```

## 2. Why this milestone exists

M003 deliberately did not cut a release merely to make its closure record look
complete. It froze and qualified the compatibility contract while leaving one
operational condition: publication of a tagged release carrying that surface.

Repository-hardening M008 subsequently repaired the Windows startup
cross-target defect and proved the seven-target release matrix green. That
removes the last known code/release-portability prerequisite.

The repository is therefore ready for a bounded publication milestone, but the
M008 qualification run is not itself release evidence for 0.4.0: the actual
release-preparation commit changes the package version and release metadata.
Per `docs/release.md`, that exact immutable candidate MUST be re-qualified
before publication and the tag MUST resolve to the recorded `QUALIFIED_SHA`.

## 8. Ordered work packages

### WP-A — Freeze release scope and reconcile metadata

1. Re-read `docs/release.md`, M003 closure, M008 closure, and the current
   registry from the candidate branch.
2. Confirm no `v0.4.0` tag exists and no crates.io 0.4.0 publication already
   exists.
3. Confirm no unreviewed production commits after this plan's baseline need to
   be included. If production code moved, audit the delta and either
   re-qualify it explicitly or stop and create a bounded corrective plan.
4. Apply only the metadata/docs changes in §7.
5. Regenerate/validate `Cargo.lock` normally.
6. Confirm:
   - `cargo metadata` reports package version 0.4.0;
   - `cargo run --locked -- --version` (or the equivalent built binary)
     reports `eggsearch 0.4.0`;
   - provider inventory is still 44;
   - the ten-tool contract is unchanged.

Commit these bytes. The resulting commit becomes the provisional 0.4.0 release
candidate.

### WP-B — Local exact-candidate verification

On a clean checkout of the provisional candidate run, at minimum:

```bash
cargo fmt --all -- --check
python3 packaging/check-workflow-pins.py
python3 packaging/check-planning-consistency.py
make check
make docs-check
make release-check
```

`make release-check` MUST include a successful
`cargo publish --dry-run --locked`.

Also run the focused CodeGG parity/provider-contract suites named by M003 (or
their current renamed equivalents) to prove that release metadata did not
accidentally change inventory or routing expectations.

Record the exact candidate SHA and all command outcomes.

### WP-C — GitHub exact-candidate binary qualification

Push the exact release candidate, then manually dispatch:

```text
Actions -> Release binaries
mode = qualify
ref  = <exact candidate SHA>
```

Require:

- preflight success;
- all seven target jobs success;
- release smoke success for each target according to the existing workflow
  contract;
- qualification assembler success;
- qualification-only artifact present;
- workflow summary `QUALIFIED_SHA` exactly equals the candidate SHA;
- no GitHub Release creation/mutation;
- no crates.io publication.

If qualification modifies or exposes a defect that requires any repository
change, the previous qualification is invalid. Commit the correction and repeat
WP-B and WP-C from the new SHA.

### WP-D — Publish crate 0.4.0

Only after WP-C succeeds on the exact candidate:

```bash
cargo publish --locked
```

Then verify through an external crates.io view/API and a clean resolver that:

- `eggsearch 0.4.0` is visible;
- the crate resolves to the intended package metadata;
- no second 0.4.0 artifact/version exists;
- the published crate contains the intended source/package files and excludes
  planning-only material according to the existing package contract.

Do not create/push the git tag until crates.io visibility is confirmed, because
the tagged release workflow intentionally fails preflight when the exact crate
version is not yet visible.

### WP-E — Tag the qualified candidate and build the binary release

Create `v0.4.0` at exactly `QUALIFIED_SHA` and push it.

Before push, mechanically verify that:

```text
tag target == QUALIFIED_SHA == release-prep candidate SHA
```

The tag-triggered `Release binaries` workflow must then:

- validate tag/version/commit/Cargo.lock/crates.io identity;
- build the seven default-feature release targets;
- run the existing CLI/MCP/health/tool-list smoke contract;
- produce checksums only after successful smoke;
- generate provenance attestations for seven executable assets and both
  installers;
- verify those attestations in-workflow;
- assemble exactly the 16 expected GitHub Release assets;
- create/update a draft release for exactly `v0.4.0`;
- refuse any attempt to overwrite an already-published release.

A release-mode workflow failure after crates.io publication is an operational
recovery problem, not permission to move the tag to different source bytes.
Repair only if the exact same qualified source can safely produce the release;
otherwise stop and prepare the next SemVer version.

### WP-F — Review and publish the immutable GitHub Release

Before manually publishing the draft:

1. Verify all 16 expected assets and filenames.
2. Verify checksum coverage.
3. Inspect workflow attestation verification output and independently sample
   verification with `gh attestation verify` for at least:
   - one Linux executable;
   - one Windows executable;
   - one installer.
4. Confirm each sample names:
   - `eggstack/eggsearch`;
   - the expected release workflow;
   - the exact qualified/tagged commit.
5. Confirm release notes correspond to the 0.4.0 changelog and do not claim a
   Google News replacement or Kagi v0 parity.
6. Publish the draft manually.
7. Confirm repository release immutability applies to the published release.

### WP-G — External install/update and CodeGG handoff smoke

After publication, exercise the public artifacts rather than local build output.

Minimum evidence:

- Unix installer fetches and installs 0.4.0 from the published release;
- Windows installer smoke succeeds through the existing supported hosted/native
  path;
- `eggsearch --version` reports 0.4.0 after fresh install;
- `eggsearch update --check` observes crates.io/GitHub release state without
  violating its exact-version/fallback contract;
- stdio MCP initialize + `tools/list` succeeds from an installed artifact;
- `provider_status` reports 44 known provider ids and contains every
  migration-relevant id named by the frozen downstream retirement contract;
- the seven newly added parity ids are present:
  `wikipedia`, `arxiv`, `pubmed`, `hn_algolia`,
  `github_repositories`, `serpapi`, and `kagi`;
- explicit unknown-provider and missing-credential behavior still uses the
  M003 stable typed failure contract.

Network-backed live searches are not required merely to prove publication.
Do not turn external provider availability into a release gate when deterministic
wire/contract qualification already exists.

## 12. Stop and recovery conditions

Stop publication and record the finding if any of these occur before
`cargo publish`:

- `make release-check` fails;
- release-binaries qualification is not fully green;
- `QUALIFIED_SHA` differs from the intended candidate;
- version/package/changelog/tag metadata disagree;
- provider inventory/tool count/migration contract drift;
- a production Rust change is needed;
- an unreviewed commit lands between candidate qualification and intended tag.

A production change requires a new candidate and full requalification. If the
change is nontrivial or changes a frozen M003 invariant, create a corrective
implementation plan rather than expanding M004 silently.

After crates.io 0.4.0 is published:

- never attempt to overwrite it;
- never force-move `v0.4.0`;
- if the release workflow fails but the same exact qualified source remains
  valid, repair/re-run the operational release path without changing source;
- if correcting source bytes is required, stop 0.4.0 release completion,
  document the partial publication, and prepare a new SemVer patch release.

After the GitHub Release is published:

- do not replace assets or tag bytes;
- any material correction requires a subsequent release.
