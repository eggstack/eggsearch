## 1. Objective

Fix the latent release-workflow attestation defect that blocked M004's binary
publication, and publish the identical CodeGG parity surface as immutable
`eggsearch 0.4.1` (crate + tag + seven-target GitHub Release with verified
provenance), supplying the release evidence M004 could not produce so that
M003 can close and CodeGG parity adoption can proceed.

`v0.4.0` stays exactly as published (crate + tag, no binaries) and is never
revisited: no tag move, no crate overwrite, no retroactive binary attachment.
The complete publication of this surface is `v0.4.1`.

The successful sequence is:

```text
fix-prep commit (0.4.1: version bump + attest-step fix only)
        |
        v
local release gates on exact candidate
        |
        v
Release binaries: mode=qualify, ref=<exact candidate SHA>
        |
        v
cargo publish --locked (0.4.1)
        |
        v
crates.io confirms eggsearch 0.4.1
        |
        v
tag v0.4.1 at exactly QUALIFIED_SHA
        |
        v
tag-triggered Release binaries workflow (release mode green incl. attest)
        |
        v
review 16-asset draft + attestations
        |
        v
manual GitHub Release publication
        |
        v
external installer/update smoke
        |
        v
closure + M003/M002 reconciliation + downstream unblock
```

## 2. Why this milestone exists

M004 proved the product side green (local gates, seven-target qualification,
crate publication) and exposed a defect strictly in release operations: the
`assemble` job's `actions/attest` v3 step cannot succeed without a
`predicate-type` the workflow never supplies, and automatic SLSA-provenance
mode does not exist in the pinned v3 action. The defect is unobservable in
qualification (attest is release-gated) and postdates `v0.3.9` (whose tag is
an ancestor of the commit that added attestation), so no prior release ever
exercised it. Full evidence is in the M004 closure record §3.

Per M004 §12, a source correction requires a new SemVer release. This plan is
that corrective release. It is deliberately narrow: one workflow repair plus
version metadata, then the standard publication sequence already validated by
M004 up to the attest step.

## 5. Invariants that MUST NOT regress

- `v0.4.0` tag bytes, crate bytes, and their identity (`81a2e49`) are never
  altered, moved, re-published, or retroactively given binaries.
- The new tag `v0.4.1` points exactly to the new `QUALIFIED_SHA`; never
  qualify one SHA and tag another.
- The published `v0.4.1` GitHub Release is manually reviewed and immutable
  after publication; exact 16-asset contract intact.
- Release-mode attestations cover the seven executables and both installers
  and verify back to this repository, the release workflow, and the exact
  candidate commit; checksums retained alongside attestations.
- Seven release targets, Linux glibc 2.17 floor, MSRV 1.89 unchanged.
- Provider inventory 44; CodeGG parity/disposition contract unchanged
  (`github_repositories` rename, Kagi current-v1 equivalent, `google_news`
  retired with no silent replacement); ten MCP tools.
- No provider, tool, request/response field, routing, cache, SSRF, updater,
  or default-provider change in this milestone.
- Published crates/tags/releases are never force-replaced; any post-publish
  correction needs a further SemVer release.

## 6. Explicit non-goals

This milestone MUST NOT:

- move, delete, or otherwise touch `v0.4.0` (tag, crate, or its records);
- attach binaries to `v0.4.0` by any out-of-band path;
- change providers, tools, schemas, routing, or the frozen disposition matrix;
- upgrade any Action other than the attestation step, or update dependencies,
  Rust versions, or unrelated release tooling;
- weaken a failing gate to preserve a version number;
- publish from a dirty tree or qualify a different SHA than the tagged one.

## 8. Ordered work packages

### WP-A — Fix scope and release-prep commit

1. Re-read `docs/release.md`, the M004 closure record, and the registry from
   the candidate branch.
2. Confirm `v0.4.0` tag still resolves to `81a2e49`, crates.io `0.4.0` is
   unchanged, and no `v0.4.1` tag/crate exists.
3. Apply only the §7 changes. Regenerate `Cargo.lock` normally.
4. Confirm `cargo metadata` and the built `--version` report `0.4.0` →
   `0.4.1` as appropriate, inventory still 44, ten tools unchanged.
5. Commit. The result is the provisional 0.4.1 candidate; record its SHA.

### WP-B — Local exact-candidate verification

On a clean checkout of the provisional candidate, at minimum:

```bash
cargo fmt --all -- --check
python3 packaging/check-workflow-pins.py
python3 packaging/check-planning-consistency.py
make check
make docs-check
make release-check
```

plus the M003-named focused suites (`web_search_integration`,
`provider_routing`, `provider_capability_contract`,
`docs_provider_inventory`, `dispatch_fault_injection`, `static_guards`).
Record the SHA and every outcome.

### WP-C — GitHub exact-candidate binary qualification

Push the candidate, dispatch `Release binaries` with `mode=qualify` and
`ref=<exact SHA>`, and require: preflight green, all seven targets green,
assembler green, `QUALIFIED_SHA` equals the candidate, qualification-only
artifact present, no release mutation, no publication. Any repository change
invalidates qualification; repeat WP-B/WP-C from the new SHA.

### WP-D — Publish crate 0.4.1

Only after WP-C: `cargo publish --locked`, then verify via external
crates.io view/API and a clean resolver that `0.4.1` is visible, resolves to
the intended metadata, and the package file set still excludes
planning-only material. Do not tag until crates.io visibility is confirmed.

### WP-E — Tag and build the binary release

Create `v0.4.1` at exactly `QUALIFIED_SHA`, verify
`tag target == QUALIFIED_SHA == candidate SHA`, and push. The tag-triggered
release workflow must go fully green **including** the repaired attest step
and in-workflow `gh attestation verify`, assemble exactly 16 assets, and
open a draft release for exactly `v0.4.1` without touching `v0.4.0`.

### WP-F — Review and publish the immutable GitHub Release

Verify the 16 assets and filenames, checksum coverage, attestation
generation/verification output (independently sample one Linux executable,
one Windows executable, and one installer with `gh attestation verify`,
confirming repository, workflow, and commit), and release notes (0.4.1 notes
plus the unchanged 0.4.0 parity description; no Google News replacement or
Kagi v0 claim). Publish the draft manually; confirm immutability.

### WP-G — External install/update and CodeGG handoff smoke

Exercise the public 0.4.1 artifacts (Unix + Windows installer smoke,
`--version` = `0.4.1`, `update --check` contract, stdio initialize +
`tools/list` = ten tools, `provider_status` = 44 ids containing the seven
parity ids, typed unknown-provider/missing-credential behavior). No
network-backed live searches as gates.

## 11. Verification matrix and stop conditions

Same matrix as M004 §11, with version `0.4.1`, qualification run on the new
candidate, and one addition: the release-mode attest step and in-workflow
`gh attestation verify` must be green (this is the regression this plan

further SemVer release. After GitHub publication: no asset/tag replacement.

## 12. Acceptance criteria

history preserved; the exact candidate passes all local gates and
binary qualification; crates.io serves `0.4.1`; `v0.4.1` points exactly to
the qualified candidate; the tag-triggered release (including attest +
verify) succeeds with exactly 16 assets; attestations verify to the expected
repository/workflow/commit; external Unix/Windows install evidence succeeds;
the installed release reports 0.4.1, ten tools, 44 providers, and the frozen
parity set; M004's blocker, M003's condition, and M002's provenance evidence
are reconciled; and registry/roadmap/closure records name CodeGG adoption as
unblocked.
