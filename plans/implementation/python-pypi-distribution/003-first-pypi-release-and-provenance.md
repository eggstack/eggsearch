## Objective and current evidence

Publish the first `eggsearch` Python wheel+sdist inventory to PyPI, allowing `pip`/`uv` consumers to install **prebuilt** artifacts for the stated supported platforms including experimental ARMv7 SBC. Protect immutability, exact-source provenance, architectural tag honesty, dependency integrity, and human approval. A published wheel and independently successful binary-only PyPI install, not a passing build, establish the user-visible capability.

Current `bindings/python` is unpublished, `pyproject.toml` / Cargo manifests use version 0.4.4, and `.github/workflows/python-native-qualification.yml` is nonpublishing. Historical M008 candidate `067468a` qualified 0.4.3 with five wheels, 20 interpreter smokes, sdist rebuild and audit; new release bytes must be requalified. The root Rust publication sequence is controlled by Eggpack and remains unchanged.

Execution added `.github/workflows/release-python-pypi.yml`. It accepts an exact candidate SHA, successful qualification run ID, and synchronized version; checks exact-SHA root CI and Python qualification; downloads only that run's artifacts; verifies the six-wheel-plus-sdist inventory and hashes; and publishes only through the `pypi` environment with OIDC permission scoped to the publish job. Post-publication binary-only consumer jobs cover five native platforms and emulated ARMv7.

The selected candidate's M001/M002 acceptance is green: Python native qualification run `40729011504` passed all 34 jobs, root CI `40729011529` passed, egress qualification `40729042102` passed, and release drift run `40729011257` passed. The exact hosted artifact set was downloaded and accepted by `verify_release_artifacts.py`; hashes and the ARMv7 audit are recorded in `plans/closure/python-pypi-distribution/001-status.md` and `002-status.md`. No M003 release-workflow run or PyPI publication has been initiated. The repository currently has no `pypi` environment configured; running the workflow before a required reviewer is configured could create an unprotected environment, so publication remains gated on maintainer setup.

## Non-goals and invariant boundaries

No automatic publish on push or Rust tag, no rewrite of existing root releases or `release/eggpack/`, no Python wheel attachment to existing Eggpack 19-asset release contract, no bundled CLI/MCP subprocess, no unconditional source-build fallback on SBC, no physical-SBC benchmark gate, no PyPy/free-threaded claim, and no release based on a different SHA than the one whose artifacts were tested.

Do not commit PyPI secrets or use long-lived API tokens when OIDC Trusted Publishing is available. Avoid mutable GitHub Action references; pin to approved 40-character commit SHAs and record upstream version. Keep permissions minimal and `id-token: write` **only in the approval-gated publish job**.

Ensure first upload will claim the intended project, not publish to an unrelated distribution. Select the exact **unused** Python version from root/binding/pyproject synchronized versions; if 0.4.4 is still the version and free on PyPI, it is eligible; otherwise plan a coherent version bump, regenerate both locks and requalify. The user's instruction to publish now is authority to prepare a publishable release; any required repository or PyPI account setup/approval must remain explicit and auditable.
2. **Implement independent trusted-publishing job.** Add e.g. `.github/workflows/release-python-pypi.yml` as the sole Python writer; use explicit `workflow_dispatch` with exact 40-hex candidate SHA and chosen version, or an immutable approved release ref resolving to that SHA. A nonpublishing qualifier produces wheels/sdist for that SHA; publish job downloads only those exact artifacts from the associated run or reconstructs at that exact SHA **and requalifies rebuilt bytes**. ## Failure semantics and publication controls

A successful wheel upload with missing mandatory target, a wheel whose platform tag does not match its linked binary, wrong source SHA, failed dependency audit, or lack of installed-consumer proof is a blocked release, not a conditional success. If PyPI name ownership or OIDC setup cannot be completed, leave release **blocked** and preserve build artifacts and exact evidence. PyPI versions are immutable: record partial uploads and choose a new release version for repairs, never attempt to replace bytes. If native ARMv7 hardware is untested but matching emulated installed-wheel acceptance passes, publication **may proceed** with explicit *experimental SBC* label. Do not expand that label to claim ARMv6/soft-float or unsupported glibc/musl environments.
