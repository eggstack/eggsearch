# Phase 3 Plan: Coding Profiles and Repo-Search Transparency

## Objective

Add named search/provider profiles and expose repo-search planning telemetry so codegg can choose the right retrieval behavior and debug misses. This phase should make `repo_search` more inspectable without changing the core safety model or forcing agents to manually specify provider IDs on every call.

The primary deliverables are:

- Named profiles: `generic`, `coding`, `security`, and `research`.
- Profile-aware provider selection with honest fallback behavior.
- `repo_search` response telemetry showing generated subqueries, intended groups, required native capabilities, and provider usage.
- Better per-result and per-response warnings when native code/search capabilities are absent.

## Current baseline

The repo already has provider descriptors and capability flags for code search, repo filters, org/path/language filters, symbol hints, issue search, release search, timestamps, freshness, and security search. `repo_search` already builds a repo search plan and iterates through subqueries, but the response does not expose those subqueries. `provider_status` reports providers, but codegg still has to reason manually about which providers to pick for a coding task.

## Non-goals

Do not change the semantics of generic `web_search`. Do not remove explicit `providers` request fields. Do not require API-backed providers. Do not add a persistent preference system. Do not make the server autonomously retry or browse recursively based on telemetry.

## Profile model

Add a `SearchProfile` enum or equivalent type:

```rust
pub enum SearchProfile {
    Generic,
    Coding,
    Security,
    Research,
}
```

Expose this as an optional request field on `web_search`, `repo_search`, `security_search`, and `research_search` where useful. It is most important for `repo_search`; the others can be conservative if avoiding churn is preferred.

Suggested behavior:

- `generic`: current default behavior; use configured default providers.
- `coding`: prefer native code/issues/releases providers when configured, then API/web providers, then generic HTML fallback.
- `security`: prefer OSV and security-capable providers, then authoritative advisory domains through generic search.
- `research`: prefer diverse source discovery and broad web/API providers.

Explicit `providers` should override profile provider selection. The response should include `profile_requested`, `profile_applied`, and `provider_selection_reason` or equivalent telemetry when a profile is used.

## Configuration

Add config support for profile provider lists without breaking current configs:

```toml
[search.profiles.generic]
providers = ["duckduckgo", "startpage", "yahoo"]

[search.profiles.coding]
providers = ["github_code", "github_issues", "github_releases", "brave_api", "searxng", "duckduckgo", "startpage"]

[search.profiles.security]
providers = ["osv", "github_issues", "brave_api", "duckduckgo", "startpage"]

[search.profiles.research]
providers = ["brave_api", "searxng", "duckduckgo", "startpage", "mojeek"]
```

Do not require these sections to exist. Defaults should be derived from enabled/configured providers and existing `default_providers`. Disabled or unconfigured API providers should be skipped with clear warnings rather than fatal errors unless explicitly requested in `providers`.

## Provider selection rules

Implement provider resolution in one place, likely near config/provider resolution logic. Avoid duplicating profile resolution inside each tool.

Resolution order:

1. If `providers` is non-empty, validate and use it exactly.
2. Else if `profile` is supplied, derive provider list from configured profile/default profile behavior.
3. Else use existing `default_providers` behavior.

When a profile contains providers that are known but unavailable because disabled or unconfigured, omit them and add a structured warning like:

- `profile_provider_unavailable: github_code is in coding profile but not configured`.
- `profile_degraded: coding profile fell back to generic providers only`.

Unknown provider IDs in config should continue to be surfaced through existing config validation or status warnings according to current repo policy.

## Repo-search subquery telemetry

Expose the plan generated by `build_repo_search_plan` in `RepoSearchResponse`. Add a serializable telemetry model such as:

```rust
pub struct RepoSearchTelemetry {
    pub profile_requested: Option<SearchProfile>,
    pub profile_applied: Option<SearchProfile>,
    pub provider_selection: ProviderSelectionTelemetry,
    pub subqueries: Vec<RepoSearchSubqueryTelemetry>,
    pub deadline_exceeded: bool,
    pub subqueries_interrupted: usize,
    pub subqueries_skipped: usize,
}

pub struct RepoSearchSubqueryTelemetry {
    pub label: String,
    pub query: String,
    pub intended_group: Option<RepoResultGroupKind>,
    pub required_capability: Option<String>,
    pub providers_attempted: Vec<String>,
}
```

If adding a nested `telemetry` field is too much, at minimum add `subqueries` to the top-level response. Prefer nested telemetry to avoid cluttering the stable response shape.

Do not include raw credentials, environment variable names, or internal HTTP URLs from private provider config in telemetry.

## Capability-aware warnings

Improve warning specificity in `repo_search`:

- Symbol hint present but no provider supports symbol hints.
- Repo/path/language hint present but selected providers cannot enforce them natively.
- Issues requested but no issue provider selected.
- Releases requested but no release provider selected.
- Coding profile requested but only generic HTML providers were available.
- Freshness requested but no provider has timestamp support or freshness filtering.

Where possible, distinguish between `not_configured`, `disabled`, and `selected_provider_lacks_capability`.

## README and host guidance

Update README compatibility guidance so codegg can follow a simple rule:

- Use `repo_search` with `profile = "coding"` for API/project/repo investigation.
- Inspect `telemetry.subqueries` and `warnings` when results are weak.
- Use explicit `providers` only for debugging or operator-directed behavior.
- Use `provider_status` to display why a profile degraded.

Add a short example response showing `profile_applied`, subqueries, and a degraded-profile warning.

## Tests

Add config/profile tests:

- Missing profile config preserves current default behavior.
- `profile = coding` selects configured GitHub providers when enabled.
- Unconfigured API providers are skipped with warnings when selected by profile.
- Explicit `providers` overrides profile.
- Unknown explicit providers are still validation errors.

Add repo-search telemetry tests with mock providers:

- Response includes generated subqueries.
- Subqueries include labels and intended groups.
- Deadline interruption counts are reflected in telemetry.
- Profile provider selection appears in response.

Add capability warning tests:

- Symbol hint with no native code provider emits symbol-specific warning.
- Issues enabled with no issue provider emits issue-specific warning.
- Releases enabled with no release provider emits release-specific warning.
- Coding profile degraded to generic providers emits profile warning.

## Acceptance criteria

- `repo_search` accepts `profile = "coding"` and applies profile-based provider selection when explicit providers are absent.
- Existing calls without profile or providers behave as before.
- `repo_search` responses include enough telemetry for codegg to show or log generated subqueries and provider degradation.
- Provider warnings are more diagnostic without becoming fatal in fallback cases.
- README documents profile use and telemetry fields.

## Suggested implementation order

1. Add `SearchProfile` type and serde parsing aliases.
2. Add profile config defaults and resolution helper.
3. Wire profile field into `RepoSearchArgs` and `RepoSearchRequest`.
4. Add telemetry structs to repo-search response.
5. Populate telemetry from repo planner and adapter dispatch.
6. Improve capability/profile warnings.
7. Add tests and README documentation.
